## Problem Statement

Chris has bigger ideas, features and new projects, that are not ready to be issues. Today the only place for them is a `proposal` issue. A proposal sits in the work store with real issues, gets parked, and has nowhere to keep the material he collects about it. He has no way to look at an idea in different ways (prior art, flaws, a picture) and keep what each look found. He also has no clean step that turns a finished idea into work for the factory.

## Solution

An idea is its own type, kept in its own git store `~/.aleph/ideas`. Each idea has a write-up, a dated log and a set of lens results. A lens is one way of looking at the idea: prior art, red team and explainer to start, each an existing skill. Chris runs a lens interactively in the idea's chat or queues it as a `lens` job. An idea never starts a code job. When Chris says so, the idea's chat builds it: the agent drafts the issues, Chris confirms, the agent files them open, and the factory starts. The UI gets an Ideas list and an idea page with tabs: Write-up, one tab per lens, Log.

## User Stories

1. As Chris, I want to add an idea with a title, a sketch and a target repo, so that I can keep a big idea outside the issue list.
2. As Chris, I want to add an idea with no target repo, so that I can keep an idea for a new project.
3. As Chris, I want to list my ideas by status, so that I see what I am exploring.
4. As Chris, I want each idea's write-up in one markdown file, so that I can read and edit it as text.
5. As Chris, I want a dated log on each idea, so that I can see the decisions and open questions in order.
6. As Chris, I want every change to an idea committed and pushed, so that ideas are never lost and have a history.
7. As Chris, I want to run a lens on an idea in the chat panel or in a terminal, so that I can work on the result with the agent.
8. As Chris, I want to queue a lens as a job, so that it runs without me and I come back to a result.
9. As Chris, I want only me to start lens jobs, so that ideas cost nothing unless I ask.
10. As Chris, I want each lens result kept with its date, so that I can compare a new look with an older one.
11. As Chris, I want the cost of each lens job recorded, so that I know what an idea has cost.
12. As Chris, I want an Ideas list in the UI with target, status, lenses, open questions and cost, so that I can see all ideas at once.
13. As Chris, I want an idea page with a tab per lens that shows the newest result and the older ones, so that I can read each way of looking at the idea.
14. As Chris, I want Run here and Queue job buttons on a lens tab, so that I can start a lens from the page.
15. As Chris, I want the chat panel on an idea page to keep one session for that idea, so that the agent remembers the idea's discussion.
16. As Chris, I want to build an idea in its chat, with the agent asking what the write-up lacks, so that the issues it files are complete.
17. As Chris, I want to confirm the drafted issues before they are filed, so that nothing starts without my yes.
18. As Chris, I want a built idea to link to its issues, so that I can follow the idea into the work.
19. As Chris, I want to drop an idea, so that dead ideas leave the list but stay in history.
20. As Chris, I want the `proposal` issue kind gone, so that the issue list holds only work.
21. As Chris, I want the issue-history plan to become an idea, so that its five parked issues leave the issue list.

## Acceptance Criteria

1. WHEN Chris runs `aleph idea add "Issue history" --target aleph --sketch -` with text on stdin THE system SHALL create `issue-history/idea.md` in the store with frontmatter `title`, `target: aleph`, `status: exploring`, `built: []`, the text as the write-up, and print the slug `issue-history`.
   - IF an idea with the same slug exists THEN THE system SHALL refuse and name the existing idea.
   - IF `--target` names a repo that is not in the registry THEN THE system SHALL refuse.
2. WHEN Chris runs `aleph idea add "<title>"` without `--target` THE system SHALL write no `target` field, and the UI and `list` SHALL show the target as "new project".
3. WHEN Chris runs `aleph idea list` THE system SHALL print one line per idea with status exploring: slug, target, lens names with results, and the date of the last change. WHEN given `--status built` or `--status dropped` THE system SHALL print only ideas with that status.
4. WHEN Chris runs `aleph idea show <slug>` THE system SHALL print `idea.md` and the list of lens results with dates. WHEN Chris runs `aleph idea edit <slug> --writeup -` THE system SHALL replace the write-up with stdin and keep the frontmatter and the log.
5. WHEN Chris runs `aleph idea note <slug> "<text>"` THE system SHALL append `- <YYYY-MM-DD HH:MM> <text>` under the `## Log` heading of `idea.md`, in local time.
6. WHEN any `aleph idea` command writes THE system SHALL make one commit in the store, whose subject names the slug and the verb, and push it IF the store has an `origin` remote. IF the store directory does not exist THEN the first write SHALL `git init` it. IF the push fails THEN THE system SHALL keep the commit and print a warning, and the command SHALL still exit 0.
7. WHEN Chris runs `aleph idea save <slug> <lens> <file>` THE system SHALL copy the file to `lenses/<lens>-<YYYY-MM-DD-HHMM>.<ext>`, where `ext` is `html` or `md` from the file name, and append a log line naming the lens. IF the extension is neither THEN THE system SHALL refuse.
8. WHEN Chris runs `aleph idea lens <slug> <lens>` THE system SHALL open a run of kind `lens` with no worktree, give the lens skill's text plus the path of `idea.md` as the prompt, and, when the run ends with a result file, save it as in 7. IF `<lens>` is not one of `prior-art`, `red-team` or `explainer` THEN THE system SHALL refuse and list the three.
9. WHILE no one asks, THE system SHALL start no lens run: no factory transition, routine or timer starts `aleph idea lens`.
10. WHEN a lens is saved twice on different dates THE system SHALL keep both files.
11. WHEN a lens run ends THE ledger SHALL hold its cost and its idea slug, and the Ideas list SHALL count that cost in the idea's Spent.
12. WHEN Chris opens `#/ideas` THE UI SHALL show one row per exploring idea with Idea, Target, Status, Lenses, Open questions, Spent and Last, and a status filter for built and dropped.
13. WHEN Chris opens `#/ideas/<slug>` THE UI SHALL show the header (title, target, status, Build) and the tabs Write-up, Prior art, Red team, Explainer, Log. A lens tab SHALL show its newest result in a sandboxed iframe and list the older results by date. A markdown result SHALL be shown as rendered markdown.
14. WHEN Chris presses Queue job THE server SHALL start `aleph idea lens <slug> <lens>` detached and the tab SHALL show the lens as running until the run ends. WHEN Chris presses Run here THE chat panel SHALL open on the idea's session and send "Run the `<lens>` lens on this idea and save the result with `aleph idea save`."
15. WHEN the chat panel is on `#/ideas/<slug>` THE panel SHALL use the session stored for that slug, and `POST /api/chat` SHALL get `idea: <slug>` and add the path of `idea.md` and the `aleph idea` commands to the prompt. WHEN Chris leaves the idea page THE panel SHALL return to the general session.
16. WHEN Chris presses Build or says "build it" in the idea's chat THE agent SHALL read the write-up and the lens results, ask about each gap it finds, and then show the drafted issues: title, kind, priority and order.
17. IF Chris has not said yes to the drafted list THEN THE agent SHALL file no issue. WHEN he says yes THE agent SHALL file each issue open in the target repo with `aleph issue add`, each after the one before with `--after`.
18. WHEN the issues are filed THE agent SHALL run `aleph idea built <slug> <ref>...`, which SHALL set `status: built` and `built: [<refs>]`, and the idea page SHALL link each ref to its issue.
19. WHEN Chris runs `aleph idea drop <slug>` THE system SHALL set `status: dropped`, keep the folder, and leave the idea out of the default list.
20. WHEN anyone runs `aleph issue add <repo> "<t>" --kind proposal` THE system SHALL refuse, and the usage text SHALL not list `proposal`. WHEN the correction memory files a lesson THE system SHALL file it as kind `task`, status parked. WHEN a `deps` or `proposal` area is read THE system SHALL map it to `task`.
21. WHEN the migration has run THE store SHALL hold an idea `issue-history` whose write-up is the text of docs/specs/2026-11-10-issue-history.md, and aleph-1679, 1680, 1681, 1683 and 1684 SHALL be dropped with a note that names the idea. `aleph issue list aleph --kind proposal` SHALL print nothing with `--status open`, `done` or `dropped`.

## Implementation Decisions

**Fixed.** The issue store and its format, `writeList`, `openRun` and `callAgent`, the ledger schema, the chat stream format, and the kit dock. The ask reason `proposal-*` and the correction-memory proposals keep their names: only the issue kind goes.

**The store.** `~/.aleph/ideas`, overridden by `$ALEPH_IDEAS`. One folder per idea, named by its slug:

```
<slug>/idea.md                       frontmatter, then the write-up, then "## Log"
<slug>/lenses/<lens>-<YYYY-MM-DD-HHMM>.html|md
```

```yaml
title: Issue history
target: aleph          # absent for a new project
status: exploring      # exploring | built | dropped
built: []              # issue refs, set by `aleph idea built`
```

The store is its own git repo, not a folder of the issue store: each top-level folder in the issue store is a repo key, and idea commits would mix into issue history. Commits and pushes go through `commitPaths` and `pushOrigin`, as the vault does. The private GitHub remote is `crsmithdev/aleph-ideas` (made 2026-11-10); the code works without one.

**The `aleph idea` command.** One new module owns the store; `jobs/commands.ts` routes `aleph idea <add|list|show|edit|note|save|lens|built|drop>` to it. Every write goes through this module. The UI and the chat agent call it; nothing writes the store by hand.

**Lens runs.** A lens is a skill name. The `lens` run kind joins `KINDS` and `ROUTINES` in lib/naming.ts, so its job IDs are `lens#<n>` and the run name is `<slug>-<lens>`. The run is opened like intake: `openRun` with no worktree, read-only tools plus Write to its run folder, the skill text as prompt text (agent roles load no skills). `$ALEPH_LENS_CMD` replaces the command in tests. The run writes its result to `result.html` or `result.md` in its run folder; `aleph idea lens` saves it with the `save` path. A run with no result file ends failed and saves nothing. Rejected: lens results as vault notes (they are per idea and dated, not facts) and lenses as factory goals (the factory only does code work).

**Who starts lenses.** Only Chris: the page buttons, `aleph idea lens`, or the chat agent when he asks. This brings back a non-code job, which "Research And Non-Code Goals Leave The Plan" (2026-11-02) removed. Chris chose this.

**Build.** No completeness bar. Build is a chat turn, not a command: the chat system prompt for an idea session states the build steps and that nothing is filed before Chris's yes. Issues are filed open, so the factory starts on them within minutes. A new-project idea cannot be built until a repo registration command exists (see Open Questions).

**UI.** A new `#/ideas` page and `#/ideas/<slug>` page, and an Ideas entry in the nav after Issues. Routes:

- `GET /api/ideas`: the list with lens names, open-question count, Spent and Last.
- `GET /api/ideas/:slug`: `idea.md` parsed, the lens results by lens and date, and running lens jobs.
- `GET /api/ideas/:slug/lenses/:file`: one result file, served with a CSP that allows no network.
- `POST /api/ideas/:slug/lenses/:lens`: queue a lens job.

"Open questions" is the count of log lines that start with `?`. Writes from the page go through the same `post` helper as other actions. Live updates use the `change` signal on `/api/events`.

**Chat.** `chat.js` gets the storage key from the page: `chat:idea:<slug>` on an idea page, the general key elsewhere. `POST /api/chat` takes an optional `idea`.

**Migration.** Code: remove `proposal` from `KINDS` in issues/lib/todo.ts, map the `deps` and `proposal` areas to `task`, file correction-memory lessons as `task` parked, and fix the two usage strings in jobs/commands.ts. Data, once, by the landing session: create the `issue-history` idea from the issue-history spec, then drop the five issues with a note that names it. 1559, 1678, 1682 and the 16 done proposals are already moved.

## Testing Decisions

A good test drives the system from outside: a CLI call, an HTTP request or a page in Chrome, and checks the files, the store's git log, the ledger or the response.

- **Seam 1, the CLI.** `run(argv, io)` in process against a temp `$ALEPH_IDEAS` with a bare repo as `origin` and a fake `$ALEPH_LENS_CMD` script that writes a result file. Covers criteria 1–11, 18–20. Prior art: issues/cli.test.ts, ui/chat.test.ts (the fake command).
- **Seam 2, the UI routes.** `withServer` over the same temp store. Covers 12–15 at the API level. Prior art: ui/issues.test.ts.
- **Seam 3, one browser test.** ui/browser.test.ts opens `#/ideas/<slug>`, checks the five tabs and that a lens tab shows its newest result in an iframe.

Build (16–17) is a prompt, not code: check it once by hand in a real chat session and report what was filed. The migration (21) is checked by the `list` command in the criterion.

## Out of Scope

- A canvas or whiteboard view of an idea.
- Lenses other than prior art, red team and explainer.
- Lens jobs started by the factory, a schedule or a threshold.
- Building a new-project idea (creating its repo).
- Parked status for ideas.
- Showing standalone explainers (`~/.aleph/explainers`) in the UI; that is the next UI step.
