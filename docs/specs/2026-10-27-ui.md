# The factory UI

Written 2026-10-27. Piece 4 of [`2026-10-25-goal-to-shipped.md`](2026-10-25-goal-to-shipped.md), second half (to-do 29). Not built.

## Problem Statement

Chris reads the factory through `aleph report`, `aleph jobs` and `aleph todo list`: three commands and JSON. The map wants one page whose front is the report: delivered, needs you, stuck, running, waiting, with the evidence for each delivery, so a spot check takes minutes.

## Solution

A local, read-mostly web page served by `aleph-ui`. Its design is `ui/prototype.html`, critiqued and polished on 27 Oct (published at https://claude.ai/artifact/YTvUknRvXSuLuFvD4vQ8gf). The prototype holds two hard-coded snapshots; the built page renders the same markup from `/api/state`.

## What this spec treats as fixed

- The ledger (`~/.aleph/jobs`), the work store and the factory directory are the only sources. The UI writes nothing of its own.
- Every action the UI offers is an existing `aleph` command, run as a subprocess: the UI adds no second path to `main`.
- The design of `ui/prototype.html`: IBM Plex Sans and Mono, Merriweather for the lede and the mark only, its colour tokens, its AA contrast, light and dark.

## Files

| File | Holds |
|---|---|
| `ui/state.ts` | `state(now)`: the `/api/state` object, read-only, from `jobs/lib` and `todo/lib` |
| `ui/server.ts` | `Bun.serve` on `127.0.0.1`: `/`, `/api/state`, and the action routes |
| `ui/index.html` | the page: the prototype's markup and styles, rendered from `/api/state`, refreshed every 15 s |
| `bin/aleph-ui` | starts the server; `--port <n>`, default `ALEPH_UI_PORT` or 3020 |

`ui/` and `bin/` are not held paths. The UI imports from `jobs/lib` and never edits it; a change the UI needs in `jobs/` is its own goal.

## `/api/state`

```ts
{
  now: string;                         // ISO
  factory: {
    paused: boolean;
    dayCap: number; runsToday: number; costToday: number;   // USD at the API price, last 24 h
    nextTick: string | null;           // from `systemctl --user list-timers aleph-tick.timer`, null when absent
    probe: { at: string; ok: boolean; failed: string[] } | null;
    health: string[];                  // the lines health() gives
  };
  needs: Job[];     // open, state needs-you
  stuck: Job[];     // open, state stuck or failed
  running: Job[];   // open, state running or passed
  delivered: Job[]; // landed in the last 24 h, latest first
  waiting: { repo: string; id: number; title: string }[];  // open goal items with no open job
  ticks: { at: string; line: string }[];                   // today's lines of tick.log
}

Job = {
  name: string; repo: string; item: { id: number; title: string } | null;
  state: string; needs?: string; phase?: string; reason?: string; question?: string;
  started: string; ended?: string; cost?: number; model?: string;
  commit?: string; commitUrl?: string;  // commitUrl from the repo's origin remote, when it is on GitHub
  defaults: string[]; followups: string[];
  stat?: string;                         // the diff stat, for needs-you
  checks?: { name: string; ok: boolean; seconds: number }[];  // when the run records them
}
```

## Views

The first version of aleph had a React UI (`~/aleph-old/src/ui`) over its own SQLite telemetry. Its routes map onto this UI as follows. The data now lives in the ledger, the work store, the registry, the vault and Langfuse, so each view reads those; none gets a database of its own.

| Old route | Old content | New view | Source now |
|---|---|---|---|
| `/summary` | goals, todos, habits, commits for 30 days | **Now** (the front page) plus a 30-day strip: goals delivered, items done, commits, runs, cost | ledger, store, `git log` |
| `/goals`, `/goals/:id` | life goals with categories and state | **Goals**: items labelled `goal`, their derived state, readiness and the `waiting_on` chain | store, `derive` |
| `/todos` | tasks and habits | **Items**: every item per repo, filtered by status, label, due; item detail with body, notes, jobs and landing commits | store, ledger, `Item:` trailers |
| (none) | | **Jobs**, **Job**: every job, and one job's runs (worker, fix rounds, review, land), result, defaults, checks, diff, logs | ledger, run folders |
| `/observability/sessions`, `:id`, `:id/turns/:n` | sessions, a session's turns, a turn's trace | **Sessions**, **Session**, **Turn**: Claude Code sessions per project, their turns, a turn's spans (tools, hooks, vault-recall) | Langfuse API |
| `/observability` | tokens, cost by model, tool and hook counts | **Activity**: cost per day and model, tool and skill counts and errors, hook runs and verify-gate denials | Langfuse API, ledger |
| `/observability/tools`, `skills`, `hooks`, `subagents` | per-capability usage | folded into **Activity**, one table each | Langfuse API |
| `/observability/memory` | memory counts, stale, search | **Memory**: the vault's notes by kind and scope, search through `vault recall`, a note with its links and backlinks, lint findings, recent writes, recall misses | vault, `vault misses` |
| (none) | | **Projects**, **Project**: each registry repo: open items and goals, last land, behind count, baseline, recent commits, vault notes in its scope | registry, store, git, vault |
| `/settings` | settings | **Controls** on the Now view: pause and resume, the judge, the caps in force | `aleph pause`, `aleph judge` |
| `/habits`, `/research/*`, `/categories`, webhooks, backup, `/observability/db`, `evals`, `learning`, `compaction`, `events` | | not carried over: habits and categories have no place in the work store; research loops return with non-code goals; learning returns with memory milestone 2 | |

**Goals and to-dos are one thing.** The work store has one kind of item; a goal is an item labelled `goal`, which the factory runs. The old UI had two tables. Here the Items view lists them all and the Goals view is the same items through the factory's lens: state, readiness, the chain.

Navigation is a sidebar in four groups: **Factory** (Now, Goals, Jobs), **Work** (Items, Projects), **Activity** (Sessions, Activity), **Memory**. Routes are hash routes (`#/jobs/aleph-52`), so the server serves one page. Each view is added to the sidebar by the goal that builds it.

## Undesigned states (from to-do 29)

## Order

Each step is one factory goal, started when the one before it has landed:

1. `ui/state.ts`, `ui/server.ts` and `bin/aleph-ui` serve `/api/state`.
2. `ui/index.html` renders the page from `/api/state`.
3. A run records each check's name, result and seconds (`jobs/lib/unit.ts`; held).
4. The actions: diff, land, drop and checked, through `aleph`.
5. The undesigned states.
6. Goals: the open goals with their derived state, and a form that files a goal item.
7. The sidebar, hash routes, and the Goals view moved to its own route.
8. Jobs and Job.
9. Items and Item.
10. Projects and Project.
11. Sessions, Session and Turn, from Langfuse.
12. Memory.
13. Activity, and the 30-day strip on Now.
14. Controls: pause, resume and the judge.

## Testing Decisions

- `ui/state.test.ts` builds a temp ledger, store and factory directory (prior art: `jobs/cli.test.ts`) and checks the object.
- `ui/server.test.ts` starts the server on a free port and fetches its routes.
- The page is checked by Chris's session in Chromium at 1440 and 390 px, light and dark: the sandbox has no browser.

## Out of Scope

- Authentication: the server binds to `127.0.0.1` only.
- Langfuse's own trace explorer: the Turn view shows a turn's spans and links to Langfuse for the rest.
- The Sidetone desktop app (piece 5).
