# Memory

Written 2026-10-27. Version 1. Piece 1 of the map, [`2026-10-25-goal-to-shipped.md`](2026-10-25-goal-to-shipped.md) ("### 1. Memory"). To-do 24.

The research is `~/.aleph/reports/Agent memory types and Notion.md`, with its notes in `~/.aleph/research_notes/Agent memory types and Notion/`. It builds on `~/.aleph/reports/Shared memory across factory agents.md`.

## Problem Statement

aleph remembers through several stores: the vault, the repos, the work store, Langfuse, the skills and the hooks. Each store grew on its own. Nothing says which store owns which kind of memory, and nothing gates most writes. Four gaps hurt Chris now:

- A future intention has no date and no trigger. "Do X after Y lands" lives in Chris's head or in a to-do that the timer cannot read.
- A fact that an agent writes to the vault carries no record of who wrote it or in which session. A new note can contradict an older note in the same scope, and the vault only warns.
- Nobody knows how often a vault search fails. The rule says to add a better retriever only when misses are frequent, but there is no count.
- Chris keeps material in Notion, and aleph cannot read it.

## Solution

One table assigns each of the seven memory types one owner, one store and one gate. No new store comes in. Milestone 1 closes the four gaps:

- A work item can carry a due date and an item it waits on. The timer starts a goal only when it is due and unblocked, and `aleph report` shows what came due.
- `vault write` records who wrote a note and in which session. Jev checks the draft against the notes it overlaps; a contradiction that `supersedes` does not name stops the write.
- The vault-recall hook records its counts in Langfuse, and `vault misses` reports four miss signals over a window of days.
- Claude reads Chris's Notion through Notion's hosted MCP server. Notion stays a source: nothing writes to it, and a fact from it enters the vault only through `vault write`, with the page URL in `sources`.

Milestone 2 adds the episode page per goal and the reviewer gate for semantic memory (see Out of Scope).

### Owner, store and gate per memory type

| Type | Holds | Owner | Store | Gate |
|---|---|---|---|---|
| Working | the context of one run | the session | the context window, handoff files | the context gate (`hooks/context-gate.ts`); handoff and pickup |
| Semantic | facts and preferences | `vault write` | vault `wiki/`, `MEMORY.md`; repo `CLAUDE.md` | `vault write` validation, provenance and the contradiction screen (M1); a fresh reviewer per fact (M2) |
| Episodic | past tasks and how they went | Langfuse and git (raw); the report writer (episodes, M2) | Langfuse traces, git, the job ledger | only the report writer writes an episode, from git, the ledger and Langfuse, never from a worker's claim |
| Procedural | rules, skills, workflows | Chris | skills, `CLAUDE.md`, hooks | a correction seen 3+ times becomes a proposal: a check first, a `CLAUDE.md` line second, a skill third; Chris approves |
| Retrieval | search over stored material | `vault recall`, the vault-recall hook | none of its own (it reads the vault) | `vault misses` decides any retriever change |
| Parametric | what the model knows | the model | the routing table (`jobs/lib/route.ts`, piece 3) | nothing is stored that the model knows; the routing table changes only by a reviewed commit |
| Prospective | future intentions | `aleph todo` | the work store (`~/.aleph/items`) | the `aleph-tick` sweep |

Notion is a source for semantic memory, not a store. Workers keep auto memory off (`autoMemoryEnabled: false` in each run's settings, set by the sandbox) and read no raw episodes.

### Milestone 2: the reviewer gate

A fact a worker learned reaches the vault only through a fresh reviewer, never on the worker's say-so.

- **The FACT line.** The worker ends its result with zero or more lines `FACT: <one sentence> [source: <file:line | commit sha | https URL>]`, for durable facts about the repo or its tools that it learned and checked. `parseFacts` (`jobs/lib/facts.ts`) reads them; a line with no source, or one that is not a repo path with an optional `:line`, a 7 to 40 hex commit sha or an http(s) URL, is unsourced: the caller logs it and nothing else sees it.
- **One reviewer per landed run.** After a run lands, one fresh Opus reviewer run checks all of its sourced facts. Its ledger kind is `facts`. It has read-only tools and gets the facts and their sources, never the worker's transcript.
- **The reply.** For each fact the reviewer answers `{fact, verdict, reason, scope, title}`: `verdict` is `keep` or `reject`, `reason` says why, `scope` says where the fact applies (the repo or global), and `title` names the page.
- **The write.** A kept fact is written with `vault write`, with `written_by: factory` and the job in `sources`. If the contradiction screen refuses the write, the fact counts as rejected.
- **Where it shows.** Rejections go to the factory log. Kept facts go to `aleph report`.
- **No yes per fact.** Chris does not approve each fact (Chris, 28 Oct); the reviewer, the source requirement and the contradiction screen are the gate.

## User Stories

### Prospective memory

1. As Chris, I want to give a to-do a due date, so that it comes back to me on that day without my keeping it in my head.
2. As Chris, I want to say that a to-do waits on another item, so that it comes back when that item is done.
3. As Chris, I want a goal item with a future due date to stay unstarted until that date, so that I can queue work for later.
4. As Chris, I want a goal item that waits on an open item to stay unstarted until that item is done, so that the factory builds in the right order.
5. As Chris, I want `aleph report` to show the items that came due or came unblocked since I last looked, so that I see them at session start.
6. As Chris, I want items that came due while the machine was off to show at the next tick, so that a missed tick loses nothing.
7. As Chris, I want to set, change and clear the due date and the waited-on item with `aleph todo add` and `aleph todo edit`, so that I never edit the store by hand.
8. As Chris, I want `aleph todo list` and `aleph todo show` to show the due date and the waited-on item, so that I can see why an item is not running.
9. As Chris, I want `aleph todo lint` to flag a bad due date or a waited-on item that does not exist, so that a typo does not hide an item forever.

### Semantic memory

10. As Chris, I want each note that an agent writes to say that an agent wrote it and in which session, so that I can trace a fact back to the turn that made it.
11. As Chris, I want my own notes, written outside Claude Code, to say that I wrote them, so that agent facts and my facts are told apart.
12. As Chris, I want `vault write` to stop a note that contradicts an existing note in the same scope, unless the new note supersedes it, so that the vault does not hold two answers to one question.
13. As Chris, I want the refusal to name the contradicted note, so that the writer can add it to `supersedes` or fix the draft.
14. As Chris, I want the contradiction screen to follow `aleph judge`, so that one switch turns every Jev use on or off.
15. As Chris, I want a Jev failure to let the write through with a warning, so that an OpenRouter outage never blocks memory.

### Retrieval

16. As Chris, I want each run of the vault-recall hook to record how many notes it considered, asked Jev about and kept, so that the filter's misses can be counted.
17. As Chris, I want `vault misses` to report the share of `vault recall` searches that found nothing, so that I know how often search fails outright.
18. As Chris, I want `vault misses` to report searches that were run again in other words in the same turn, so that I see searches that found the wrong thing.
19. As Chris, I want `vault misses` to report vault notes that were read in a turn where neither search nor the hook offered them, so that I see notes the retrieval missed.
20. As Chris, I want `vault misses` to report how often the hook found no candidate and how often it hit its cap of 40, so that I know which stage of the filter loses notes.
21. As Chris, I want `vault misses` to take a window in days, so that I can compare weeks.

### Notion

22. As Chris, I want Claude to search and read my Notion pages in a session, so that material I keep there is usable without copying it.
23. As Chris, I want aleph never to write to Notion, so that Notion stays my space and the vault stays the one store of facts.
24. As Chris, I want a fact that Claude takes from Notion into the vault to cite the Notion page URL, so that the source is one click away.

### Rules held

25. As Chris, I want each factory worker to run with auto memory off, so that a worker never writes memory where it reads its orders.
26. As Chris, I want the memory table in this spec to be the one place that says who owns what, so that a later piece cannot add a store without changing it.

## Acceptance Criteria

### Prospective memory

1. WHEN Chris runs `aleph todo add <repo> "<title>" --due 2026-11-02` THE item SHALL carry `due: 2026-11-02` in its frontmatter, and `aleph todo show` SHALL print it.
2. WHEN Chris runs `aleph todo add <repo> "<title>" --waiting-on aleph-36` THE item SHALL carry `waiting_on: aleph-36`. `waiting_on` names one item as `<repo>-<n>`.
3. IF a goal item is open and its `due` is after today THEN `aleph tick` SHALL not start it and SHALL list it under `skipped` as `<name>: due <date>`.
4. IF a goal item is open and the item it waits on is not done THEN `aleph tick` SHALL not start it and SHALL list it under `skipped` as `<name>: waiting on <repo>-<n>`. WHEN that item is done (by the derived state of `aleph status`) THE next tick SHALL start it.
5. WHEN an open item's `due` is today or earlier, or the item it waits on became done, THE next `aleph report` SHALL list it once under a "came due" line with its number and title, and later reports SHALL not repeat it.
6. WHEN the tick runs after a gap of several days THE report SHALL list every item whose `due` fell in the gap. A test sets the clock past three due dates and sees all three.
7. WHEN Chris runs `aleph todo edit <repo> <n> --due none` (or `--waiting-on none`) THE field SHALL be removed. `--due` takes only `YYYY-MM-DD` or `none`; anything else SHALL be refused with exit 1.
8. WHEN `aleph todo list` prints an item with `due` or `waiting_on` THE line SHALL show `due <date>` or `waits <repo>-<n>`.
9. WHEN `aleph todo lint` finds a `due` that is not a valid date, or a `waiting_on` naming an item that does not exist, THE lint SHALL report it as a finding with the item number.

### Semantic memory

10. WHEN `vault write` runs with `CLAUDE_CODE_SESSION_ID` set THE written note SHALL carry `written_by: claude` and `session: <that id>` in its frontmatter, unless the draft already sets `written_by`.
11. WHEN `vault write` runs without `CLAUDE_CODE_SESSION_ID` THE note SHALL carry `written_by: chris` and no `session`.
12. WHEN a draft shares a scope with a live wiki note and the two share a word of four or more letters in their titles or aliases, and Jev answers p ≥ 0.7 to "Does the draft's claim contradict the note's claim?", and the draft's `supersedes` does not name that note, THEN `vault write` SHALL refuse with exit 1 and change nothing on disk.
13. WHEN the screen refuses THE message SHALL name each contradicted note by title and say "add it to supersedes or fix the draft".
14. WHILE `aleph judge` is `haiku` THE screen SHALL not run, and `vault write` SHALL behave as before this spec. The screen asks at most 20 notes in one Jev request.
15. IF the Jev request fails THEN `vault write` SHALL write the note and print a warning naming the failure.

### Retrieval

16. WHEN the vault-recall hook runs THE turn's Langfuse trace SHALL get a `vault-recall` span with metadata `candidates` (notes with a word hit, before the cap), `asked`, `kept` and `capped` (true when candidates exceeded 40). A test with a fake Langfuse server sees the span.
17. WHEN Chris runs `vault misses --days 7` THE output SHALL be JSON with `recalls` (count of `vault recall` Bash calls in the window), `empty` (calls whose output was `[]`) and `empty_share`.
18. THE output SHALL also carry `reformulated`: turns with two or more `vault recall` calls where the first returned `[]` or was followed by a call with different words.
19. THE output SHALL also carry `unoffered_reads`: Read calls on a vault `wiki/` file in a turn where neither a `vault recall` output nor the hook's injected context named that note.
20. THE output SHALL also carry `hook`: the count of hook runs, of runs with zero candidates, of capped runs, and the mean of `kept`.
21. WHEN `--days` is missing THE window SHALL be 7 days. The command reads Langfuse through the API the hooks already use and writes nothing.

### Notion

22. WHEN Chris runs `claude mcp list` THE list SHALL show a `notion` server at `https://mcp.notion.com/mcp` with user scope, connected after Chris's OAuth login (a manual step).
23. WHEN `git grep -n "notion"` runs in aleph after milestone 1 THE only hits SHALL be docs and this spec: no code calls the Notion API and no hook writes to Notion.
24. WHEN a vault note's `sources` holds a `notion.so` or `notion.site` URL THE `vault write` validation SHALL accept it as a source, as it accepts any URL.

### Rules held

25. WHEN the sandbox makes a run folder THE run's Claude Code settings SHALL hold `autoMemoryEnabled: false`. A test reads the settings file the run folder holds.
26. WHEN `git grep -n "Owner, store and gate"` runs in aleph THE only definition of the table SHALL be in this spec; the map links to it.

## Implementation Decisions

- **Work store fields.** Two optional frontmatter fields on an item: `due` (a date, `YYYY-MM-DD`) and `waiting_on` (one `<repo>-<n>`). One waited-on item, not a list: a list has had no use yet. Backlog.md ignores unknown fields, so its board keeps working.
- **Readiness lives in the tick.** `tick` in the factory library already skips paused runs and the day cap; it gains two skip reasons, due and waiting. "Done" for `waiting_on` is the derived state from `aleph status` (trailers on `origin/main`, the store, the ledger), not only the store's status.
- **"Came due" is shown once.** The factory directory keeps a small seen file of item ids that have been reported as came due, like the ledger's `shown` flag on runs. The report reads it and writes it. This is not a new memory store: it holds display state, as `shown` does.
- **Catch-up.** The sweep compares `due` with today, so any tick after a gap catches every item in the gap. The timer's `OnBootSec` already gives a tick after boot.
- **Provenance.** `vault write` stamps `written_by` (`claude` or `chris`) and `session`. It does not stamp the model: Langfuse holds the model per session, and a second copy could disagree. Both fields are optional in the note schema, so the 256 existing notes stay valid.
- **The contradiction screen.** It reuses the overlap rule that lint already warns on (same scope, a shared title or alias word), sends one Jev request with one `noul` per overlapping note (at most 20), and refuses at p ≥ 0.7. It runs before any disk change, as the other refusals in `vault write` do. It follows `judgeChoice()`.
- **The recall span.** The hook posts one span to the turn's trace with the OTLP helper that `hooks/obs.ts` uses. Langfuse owns runtime records; no local log file is added.
- **`vault misses`.** A new read-only `vault` subcommand that pages through Langfuse observations for the window. It derives the four signals from Bash observations whose input starts with `vault recall`, from Read observations on `wiki/` paths, and from the `vault-recall` spans.
- **Notion.** User-scope MCP config only: `claude mcp add --transport http --scope user notion https://mcp.notion.com/mcp`, then Chris logs in through `/mcp`. On Free or Plus, the API's search matches titles only and allows 3 requests a second; the hosted MCP server's own search is the better path. Rejected: a push script to Notion (a view) and two-way sync. Chris chose source only on 27 Oct.
- **Rejected:** a vector or graph database (the vault is about 140k tokens, under the size where retrieval beats reading); fine-tuning for memory; episodes that an agent picks for itself (they scored below no memory, 22.2% against 26.3%, SWE-ContextBench).

## Milestone 2: correction mining

The Procedural row of the table is made real: repeated corrections become proposals that Chris decides.

- **Three sources.** Chris's pushback in sessions (Langfuse), the verify gate's denials (Langfuse), and the reasons runs were dropped (the ledger). Each is a signal with a quote and a link.
- **Jev's part.** Jev screens each message for a correction (a `noul` per message, p ≥ 0.7), chooses which lesson a signal joins or whether it starts a new one (the grouping choice), and answers the kind questions when a lesson reaches the threshold.
- **The store.** `corrections.json` in the factory directory holds `minedAt` and the lessons, each with its sentence, signals, count and state (`open`, `proposed`, `approved`, `declined`). Signals are kept for 14 days of mining window; a signal already stored is never counted twice.
- **The threshold** is the setting `ALEPH_PROPOSE_AT` (default 3). An open lesson with that many signals becomes a proposal.
- **Order of preference of kinds.** A check first (a test or lint can catch it), a `CLAUDE.md` line second (one rule states it), a skill third. If Jev fails on a lesson it stays open.
- **The daily step.** The first tick after 03:00 local that finds `minedAt` empty or on an earlier local date runs the mining, under the pause and probe gates. It logs `corrections: <n> signals, <m> lessons, <k> proposed`; an error is logged and never fails the tick.
- **The report.** `aleph report` lists every pending proposal, on each report, until Chris decides it, in a block `proposed lessons (Yes or No on Status):` with one line `<id> <kind>: <sentence> (<count> signals)`. No proposal, no block.
- **Deciding.** The Status page shows a Decide row for each proposal, with Yes and No. Yes files a goal issue for the change; No declines the lesson for good.
- **The rule.** Nothing changes a `CLAUDE.md`, a skill or a check without Chris's Yes.

## Testing Decisions

- A good test drives a command or a hook from outside and checks what Chris would see: CLI JSON, the store file, the vault file, a span posted to a fake server. No test reaches into a module's internals.
- **Seam 1, the aleph CLI** (`aleph todo`, `aleph tick`, `aleph report`) on a temp registry, store and factory directory, with a fixed clock. Prior art: `jobs/cli.test.ts`.
- **Seam 2, the vault CLI** (`vault write`, `vault misses`) on a temp vault, with a fake Jev server and a fake Langfuse server. Prior art: `vault/cli.test.ts`, `hooks/lib/judge.test.ts`.
- **Seam 3, hooks as subprocesses** with fake Jev and Langfuse servers. Prior art: `hooks/vault-recall.test.ts`, `hooks/obs-task-type.test.ts`.
- Notion is checked by hand: `claude mcp list` shows the server connected, and one session reads a page.

## Out of Scope

- **Episode pages** (one per finished goal, by the report writer). Milestone 2, when the report writer exists.
- **Working memory changes.** The context gate and handoffs stay as they are. Capping and clearing tool output is a later goal.
- **Writing to Notion** in any form, and Notion Agent memory.
- **Event triggers other than "item done"** (a commit lands, a file changes).
- **Upgrading Langfuse to v4.** Local Langfuse is v3.225.4; Langfuse Cloud drops the v1 API on 16 Nov 2026, which does not touch a local v3 instance. Decide when the local instance is upgraded.

## Open Questions

- **The promotion threshold** (a correction seen 3 or more times becomes a proposal). No study gives a number. The threshold is now the setting `ALEPH_PROPOSE_AT` (default 3), to be read from real counts once the mining has run for a few weeks.
- **When `vault misses` justifies a new retriever.** No published threshold exists. Unblocks after two weeks of counts: Chris sets the bar from the first real numbers.
