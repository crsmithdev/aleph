Aleph

Claude Code writes code. Herdr runs many sessions at your desk. Neither tool moves work between your desk and your telephone. Aleph moves the work. This is its purpose, and the six workflows below are the full test of it.

The six workflows

What Aleph must do, in order of difficulty

Aleph does not do these things yet. Each one is a target. The first two are almost not Aleph's work at all — that is the correct result. The last two are the reason it exists.

The rule this makes. A pane that never speaks to Aleph must work correctly. At your desk Aleph is present, but it is passive.

The rule below all six

Each job has one driver

The mirror

The topic list is the state of your machine

The group holds a topic for each job that the daemon drives and for each local session that parked. Thus the work that you start at your desk is on your telephone before you look for it.

EventThe topic
A session parks, or a job startsAleph makes the topic.
You send a message, and no process holds the worktreeAleph attaches the session and starts the turn.
You hold the paneThe headline says so. A message gets a refusal that tells you where the pane is.
The work merges, or you drop itAleph closes the topic. Telegram keeps the history.
The session stops with work not committedThe topic stays open.
AnythingAleph never deletes a topic. The history is context.
it deletes

Three steps that you no longer do

The adopt tool, the question “what is in progress?”, and the answer “take 1”. Your first message in the topic replaces all three.

it costs

A watcher that runs all day

This is more machinery, not less. Aleph keeps the cost small with two rules: it summarizes one time for each park, and it makes a topic only for a session that looks parked.

decide on purpose

Data leaves the machine all day

Before the mirror, only the work that you dispatched went to Telegram. Now your repository names, branch names and activity go there at each park. config.toml can exclude a repository, and an excluded repository gets no topic.

The machine

The daemon holds the conversation. The CLI does the code.

Knowledge

Aleph writes the facts. You write the procedures.

Memory is facts and Aleph writes them. Skills are procedures and you write them. This difference is on purpose. A fact is easy to examine and easy to delete, thus Aleph can write one without permission. A skill changes how Aleph operates, thus it arrives as a file that you merge, and in no other way.

no chat interface

Two protocols instead

The bridge gives your panes Aleph's facts, on your subscription, from M0. The endpoint gives any client Aleph's agent, from M1. A REPL written here would compete with llm and aichat and lose. For “is the loop alive”, the answer is aleph doctor.

the memory bridge

Your panes read the same facts

A herdr pane is a usual Claude Code session, thus it cannot reach the daemon. A small MCP server corrects this. It gives recall, remember and job_status to each pane. It does not start jobs — you are at a keyboard already.

a fact

Aleph writes it, you examine it after

Aleph shows you each write, and aleph memory lists them all. A wrong fact costs you one line to delete.

a procedure

You write it, Aleph reads it

To make a skill is a job, and a job stops at a change that you must merge. Nothing that changes how Aleph operates enters without your approval.

Landing

The repository says what is enough

Only a person merges a branch, and Aleph has no tool to merge. That does not change. But the quantity of examination that is enough changes with the work, thus the policy belongs to the repository and not to Aleph.

Class of changeWhat is enough from the telephone
documentsThe list of changed files.
logicThe verification gate of the repository is green, and you read the difference.
migration · releaseNothing. Keep the job for your desk.

Each repository holds its own policy, in the file that says how to verify a change there. Aleph reads that file and does not make a second rule. A job proposes its class and shows the evidence. You can always move a job down to “keep it for the desk”. You cannot move it up.

State

Each thing that Aleph knows is a file

~/.aleph-next/ soul.md the identity. each conversation turn starts with it config.toml the group · the repositories · the models · the rules conversations/*.jsonl the transcript of the daemon. this is the truth memory/*.md one fact in one file skills/<name>/SKILL.md procedures. a link makes them global jobs/<id>/ task.md · state.json · stream.jsonl (20 MB maximum) events.jsonl each message · permission · job change · cron start index.db an index. if you delete it, aleph builds it again

The files are the truth. When Aleph builds the index again, it ignores a bad last line and gives a warning. It does not stop — which is the defect in workflow 2.1.

the event log

Five rules, kept on purpose

One emit path. Every event names its cause, so the log is a graph and not a list. The JSONL is truth and the index rebuilds. Redaction before the write. And every event carries its trace ID.

one trace

A job's spans nest inside yours

The daemon sets TRACEPARENT when it spawns a job, and claude_code.interaction lands as a child of the daemon's span, in the daemon's trace. Tested, not assumed. Traces on, logs off — one two-word turn emitted 58 KB of logs against 4 KB of traces.

threads

One type, two kinds

A job is a thread of kind code — a worktree, a branch, a CLI session, and the driver rule. The General topic is a thread of kind chat, which has none of those and needs no driver rule. One store, one ID space.

Build order

Each milestone is useful alone

  1. M0 The loop, aleph chat, memory, the skill index, events It remembers between restarts, and you can teach it a procedure
  2. M1 The loop, Telegram, topics, pairing, the OpenAI-compatible endpoint You use it from your telephone for one week
  3. M2 Jobs, the caps, attach / diff / land / drop It corrects a true defect in this repository — workflows 2.3 and 2.6
  4. M3 The mirror: the watcher, the park rule, the summary, attach from a message Workflow 2.5, done from a train
  5. M4 The permission gate, permissions in Telegram, secret removal You can leave it without supervision
  6. M5 Cron, schedule Aleph speaks first

M0 has no loop. The bridge needs none — a pane brings its own model and reaches Aleph only for facts. The loop arrives at M1, because Telegram is the first surface with no Claude Code on the other end, and the endpoint rides along with it as one more transport over the same loop.

M2 is safe before the gate because the job design contains it: a worktree, no credentials, no way to merge, and three caps — three jobs at one time, one per repository, one started in a turn. When a cap blocks a job, Aleph refuses and names it. It does not queue.

Posture

What this does not protect you from

no sandbox

A job runs as you

The same user, the same disk, no container in v0. Each control here is a fence, not a wall. Hermes says the same about itself.

one group

Membership is the credential

Aleph replies only in the supergroup that you paired, and refuses each direct message. To add a person to that group is to give that person your machine. Keep it private.

adoption has a limit

It reads only what you named

To offer a session, the daemon must look at the sessions on disk. It looks only inside the repositories in config.toml. It must never index what you did not give it.

Hermes Agent (Nous Research) is the reference shape: a gateway, an agent loop, files for memory and skills, cron, a soul. Aleph keeps that shape and gives the code to claude.
