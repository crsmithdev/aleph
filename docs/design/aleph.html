Aleph

Claude Code writes code. Herdr runs many sessions at your desk. Neither tool moves work between your desk and your telephone. Aleph moves the work. This is its purpose, and the six workflows below are the full test of it.

The six workflows

What Aleph must do, in order of difficulty

Aleph does not do these things yet. Each one is a target. The first two are almost not Aleph's work at all — that is the correct result. The last two are the reason it exists.

2.1

One local session

a herdr pane
herdr · pane 1 · ~/aleph-next
$ claude › the reindex stops on a torn last line. skip it and give a warning. ▸ Read src/core/eventlog.ts ▸ mcp__aleph__recall "how does chris merge?" → package manager is bun. merges are squashed. ▸ Edit src/core/eventlog.ts ▸ Bash bun test → 12 pass $ git commit -am "skip a torn line, warn" && gh pr create
The rule this makes. A pane that never speaks to Aleph must work correctly. At your desk Aleph is present, but it is passive.

The rule this makes. Aleph offers to adopt when you arrive, not when you leave. It must not interrupt you at your desk. Before it takes a session, it reads /proc to prove that no process holds that worktree. It does not use your word for this.
2.6

A mobile session that continues at your desk

terminal, then herdr

$ aleph jobs 91c2 waits 18m aleph-next log-size dispatched a0d7 runs 4m dotfiles fish-migration dispatched 4e81 waits 2h aleph-next torn-line adopted $ aleph attach 91c2 the daemon stopped its process. you are the driver now. herdr: a new pane, in .worktrees/job-91c2 claude --resume 3f0e2c81-…

The session does not change. It keeps the same transcript, the same skills and the same CLAUDE.md. This is easy because the daemon started the job: it knows the session ID, and it made the worktree. Workflow 2.5 is the difficult direction.

The rule below all six

Each job has one driver

The machine

The daemon holds the conversation. The CLI does the code.

Knowledge

Aleph writes the facts. You write the procedures.

Memory is facts and Aleph writes them. Skills are procedures and you write them. This difference is on purpose. A fact is easy to examine and easy to delete, thus Aleph can write one without permission. A skill changes how Aleph operates, thus it arrives as a file that you merge, and in no other way.

the memory bridge

Your panes read the same facts

A herdr pane is a usual Claude Code session, thus it cannot reach the daemon. A small MCP server corrects this. It gives recall, remember and job_status to each pane. It does not start jobs — you are at a keyboard already.

a fact

Aleph writes it, you examine it after

Aleph shows you each write, and aleph memory lists them all. A wrong fact costs you one line to delete.

a procedure

You write it, Aleph reads it

To make a skill is a job, and a job stops at a change that you must merge. Nothing that changes how Aleph operates enters without your approval.

Landing

The repository says what is enough

Only a person merges a branch, and Aleph has no tool to merge. That does not change. But the quantity of examination that is enough changes with the work, thus the policy belongs to the repository and not to Aleph.

Class of changeWhat is enough from the telephone
documentsThe list of changed files.
logicThe verification gate of the repository is green, and you read the difference.
migration · releaseNothing. Keep the job for your desk.

This repository has docs/VERIFICATION.md already. Aleph reads that file and does not make a second rule. A job proposes its class and shows the evidence. You can always move a job down to “keep it for the desk”. You cannot move it up.

State

Each thing that Aleph knows is a file

~/.aleph-next/ soul.md the identity. each conversation turn starts with it config.toml the group · the repositories · the models · the rules conversations/*.jsonl the transcript of the daemon. this is the truth memory/*.md one fact in one file skills/<name>/SKILL.md procedures. a link makes them global jobs/<id>/ task.md · state.json · stream.jsonl (20 MB maximum) events.jsonl each message · permission · job change · cron start index.db an index. if you delete it, aleph builds it again

The files are the truth. When Aleph builds the index again, it ignores a bad last line and gives a warning. It does not stop — which is the defect in workflow 2.1.

Build order

Each milestone is useful alone

  1. M0 The loop, aleph chat, memory, the skill index, events It remembers between restarts, and you can teach it a procedure
  2. M1 The Telegram group, topics, pairing You use it from your telephone for one week
  3. M2 Jobs, attach / diff / land / drop, the memory bridge It corrects a true defect in this repository — workflows 2.3 and 2.6
  4. M3 The permission gate, permissions in Telegram, secret removal You can leave it without supervision
  5. M4 Adoption, cron, schedule Workflow 2.5, and one week of morning reports

M2 is safe before M3 because the job design contains it: a worktree, no credentials, and no way to merge.

Posture

What this does not protect you from

no sandbox

A job runs as you

The same user, the same disk, no container in v0. Each control here is a fence, not a wall. Hermes says the same about itself.

one group

Membership is the credential

Aleph replies only in the supergroup that you paired, and refuses each direct message. To add a person to that group is to give that person your machine. Keep it private.

adoption has a limit

It reads only what you named

To offer a session, the daemon must look at the sessions on disk. It looks only inside the repositories in config.toml. It must never index what you did not give it.

Hermes Agent (Nous Research) is the reference shape: a gateway, an agent loop, files for memory and skills, cron, a soul. Aleph keeps that shape and gives the code to claude.
